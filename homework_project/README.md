# Курсова — НРК розмінувальник (симуляція, спрощений варіант)

Автономний рух мобільного робота по заданому периметру в Gazebo,
з перехопленням керування оператором, HTTP-звітуванням та логуванням у rosbag.
Платформа — TurtleBot3 у симуляції (без реальної броньованої машини).

## Місце проєкту і що було б далі

Це початковий, базовий етап для побудови складної системи автономного
руху мобільного робота по заданому периметру. Головне, що зроблено тут
правильно і без чого не обійтись далі: логіка відокремлена від ROS,
режими autonomy/manual переключаються однією HTTP-командою, все
логується у rosbag і покрито тестами.

Етапи, які важливо було б додати (бажалося, але не встигли):

- **об'їзд перешкод** — використати /scan (він вже пишеться у баг):
  простий reactive-об'їзд (стоп-модифікатор швидкості) на перший час,
  далі Nav2 з costmap — вже без змін у ядрі логіки, бо вона не знає
  про ROS;
- **точніше позиціонування** — одометрія у симуляції ідеальна, на
  реальній платформі попливе; потрібен GPS/SLAM як джерело позиції
  замість /odom (в ядрі міняється тільки вхід update(x, y, yaw));
- **щільніший маршрут** — зараз 4 точки прямокутника; для "розмінування"
  ділянку проходять смугами (lawnmower pattern) або з адаптивним
  кроком — це новий список waypoint-ів, логіка та сама;
- **виявлення об'єктів** — детектор металу/камера + призупинення
  патруля і статус "detected" у HTTP-звіті, а далі і первинний огляд
  перед викликом оператора;
- **стійкість зв'язку** — зараз HTTP у "питання-відповідь"; треба
  буферизацію звітів при обриві каналу і heartbeat, щоб оператор
  бачив "мертвого" робота відразу;
- **безпека на борту** — watchdog: якщо автономія "зависла" або
  зв'язок обірвався надовго — робот сам зупиняється;
- **перенесення на реальну платформу** — замінити симуляційне шасі
  реальним (джерело /odom і /cmd_vel), логіка і HTTP-звіт
  залишаються як є.

## Структура

Все вміщується в один пакет `patrol_bot` у звичайному colcon-воркспейсі
(`homework_project/robot_ws`).

- `setup_env.sh` — ставить ROS2 Jazzy, Gazebo, TurtleBot3 (один раз);
- `run_all.sh` — стартує все: збірка > Gazebo > ноди > rosbag-запис;
- `robot_ws/src/patrol_bot/include/patrol_bot/patrol_controller.hpp` —
  ядро логіки;
- `robot_ws/src/patrol_bot/src/patrol_mission_node.cpp` — ROS-вузол
  автономії;
- `robot_ws/src/patrol_bot/src/http_status_node.cpp` — HTTP API;
- `robot_ws/src/patrol_bot/test/patrol_controller_test.cpp` — gtest-и;
- `robot_ws/src/patrol_bot/tools/offline_check.cpp` — перевірка логіки
  без ROS;
- `robot_ws/src/patrol_bot/launch/patrol.launch.py` — запуск обох вузлів;
- `bags/` — записані rosbag-и.

Далі — що саме в кожній частині.

**Ядро логіки** (`patrol_controller.hpp`, header-only): периметр як список
точок, P-контролер (спершу поворот на місці, потім їзда вперед, перехід до
наступної точки), режими PATROL/MANUAL, підрахунок пройденого шляху.
Клас нічого не знає про ROS — тому його можна тестувати gtest-ом і ганяти
офлайн без Gazebo.

**ROS-вузол автономії** (`patrol_mission_node.cpp`): читає `/odom`, раз на
100 мс публікує `/cmd_vel` (тип `TwistStamped` — так вимагає міст Gazebo
у Jazzy), раз на секунду пише стан у `/ugc_status` (JSON), слухає
`/ugc_mode`. Жодної логіки "як їздити" в ньому немає — тільки обгортка.

**HTTP API** (`http_status_node.cpp`, cpp-httplib, port 8080): `GET /status`
і `/perimeter` віддають останній стан, `POST /mode` переключає режими.
Міст між ROS і зовнішнім спостерігачем (командним пунктом).

**Тести й перевірки:** 6 gtest-ів на контролер (повороти, обмеження
швидкостей, перехід точок, блокування команд у MANUAL) плюс офлайн-симуляція
проїзду периметру в терміналі — без ROS і без Gazebo.

## Як запустити

```bash
bash setup_env.sh        # один раз; потім перезайти в термінал

bash run_all.sh          # Gazebo + ноди + rosbag одним скриптом
```

Після запуску:

```bash
curl http://localhost:8080/status     # режим, позиція, поточна точка, шлях
curl -X POST http://localhost:8080/mode -d '{"mode":"MANUAL"}'   # перехопити
curl -X POST http://localhost:8080/mode -d '{"mode":"PATROL"}'   # відпустити
ros2 run teleop_twist_keyboard teleop_twist_keyboard             # ручне керування
```

## Перевірка без ROS

```bash
cd robot_ws/src/patrol_bot
clang++ -std=c++20 -O2 -I include tools/offline_check.cpp -o /tmp/offline_check
/tmp/offline_check
```

## Алгоритм

P-контролер, патерн mission_controller з ДЗ14:

1. обчислити кут до поточної точки периметра; якщо похибка > 0.08 рад —
   поворот на місці (обмежено 0.8 рад/с);
2. інакше — рух уперед зі швидкістю пропорційно відстані (макс 0.3 м/с);
3. відстань < 0.15 м — точка досягнута, перехід до наступної (по колу, 4 точки);
4. режим MANUAL — вузол не публікує /cmd_vel, керує оператор; PATROL — назад.

## Що зроблено (все перевірено у симуляції)

- **автономний рух по заданому периметру** — 4 точки прямокутника
  (±1.5, ±1.5), P-контролер (поворот на місці > рух вперед), обхід по колу;
- **перехоплення керування оператором** — `POST /mode {"mode":"MANUAL"}`
  зупиняє автономію, робота керують teleop-ом; `{"mode":"PATROL"}` —
  продовження з поточної позиції;
- **звіт про рух у API по HTTP** — `GET /status` (режим, позиція, поточна
  точка, пройдений шлях), `GET /perimeter`, `POST /mode` — на cpp-httplib,
  без зовнішніх залежностей;
- **збір даних у rosbag** — `/odom`, `/scan`, `/cmd_vel`, `/ugc_status`,
  `/ugc_mode` записуються автоматично (`bags/`);
- **симуляція** — TurtleBot3 у Gazebo (Jazzy), запуск одним скриптом
  `run_all.sh`;
- логіка винесена з ROS: gtest (6/6) і офлайн-перевірка без ROS
  (`tools/offline_check.cpp`).

## Навіщо це мілтеху / задачі "розмінувальник"

Задача: *прихований НРК розмінувальник, що рухається по заданому периметру
автономно або з перехопленням оператора, звітує по HTTP і логує в rosbag,
зі симуляцією*.

1. **Патрулювання по периметру — це каркас маршруту розмінування.**
   Реальний розмінувальник об'їздить задану ділянку смугами/контуром.
   Замінюються 4 точки на щільнішу сітку waypoint-ів — сама логіка
   "їдь у точку > наступна" не змінюється, бо вона винесена в окремий
   протестований клас `PatrolController`.

2. **Перехоплення керування — критична функція безпеки.**
   Розмінувальник у поля зобов'язаний давати оператору можливість забрати
   керування за секунду (перешкода, підозрілий об'єкт, застряг).
   Тут режим MANUAL/PATROL переключається HTTP-командою, і автономія
   гарантує нуль команд у `/cmd_vel` у ручному режимі — це перевірено
   юніт-тестом.

3. **HTTP-звіт — стійкий канал C2.** HTTP простий, працює через будь-які
   мережі і легко обгортається у TLS/VPN; формат статуса вже задає
   мінімальний контракт "апаратура > командний пункт".

4. **rosbag — чорна скринька.** Запис одометрії, скану і команд дає
   розбір будь-якого інциденту "після факту" і тренувальні дані
   (у реальному розмінувальнику сюди додадуться кадри з камер/детектора).

5. **Симуляція спершу — безпека і швидкість розробки.** Жодна перевірка
   автономії, перехоплення чи логування не потребує реального шасі;
   налаштування з симуляції переносяться на платформу без змін коду
   (міняється тільки джерело одометрії).

Навмисні спрощення (без енергозбереження і оптимізації, за умовою):
симуляційна платформа замість броньованої, без об'їзду перешкод,
без GPS/SLAM, без детектора і маніпулятора.

## Спрощення (навмисно, для курсової)

- без об'їзду перешкод, GPS/SLAM — одометрія Gazebo;
